# AnswerCanvas Codex Instructions

## Image-to-handwritten recreation workflow

When the user uploads a notebook/reference image and asks to “转成手写”, “复刻”, “做成可播放手写版本”, or equivalent:

1. **Never overwrite an existing scene.** Existing scenes are historical outputs and must stay reproducible.
2. Read `docs/superpowers/specs/2026-08-07-multi-scene-recreation-design.md` before editing. If the task is a learning/analysis walkthrough (grammar, formula, code, chart, process, etc.), also read `docs/superpowers/specs/2026-08-07-immersive-analysis-playback.md`.
3. Inspect the image semantically, not only with OCR. Identify page structure, text blocks, explicit line breaks, Cue/Notes relationships, annotations, boxes, arrows, diagrams, colors, and a plausible human writing order.
4. Create one new file under `features/recreation/scenes/<scene-id>.ts`. Use a canonical lowercase kebab-case scene ID and preserve the source image aspect ratio in `width`/`height` unless the user explicitly asks for a video-first paged layout.
5. Give every new scene a concise `prompt` that reads like the user's original request. The scene page renders this prompt as the user message above the handwritten answer, while `title` remains the short history label.
6. Rebuild the image with HTML text and SVG geometry. **Do not use the source image as the page background.** Use authored scene coordinates rather than browser auto-layout for source-critical placement.
7. Put permanent page structure (page border, column dividers, section separators, paper pattern) in elements with `animated: false` and no `order`.
8. Put text, annotations, arrows, icons, explanatory diagrams and other pen-created content on the single animation timeline. Dynamic `order` values must be finite, non-negative and unique in the scene.
9. A single virtual pen is the invariant: no two pen-created dynamic elements may intentionally animate concurrently. Preserve explicit source-image line breaks. On ruled paper, use `snapToRule: true` only when the source text is actually aligned to those rules; otherwise preserve authored coordinates. For underlines/highlights/circles, prefer semantic `targetId + match` marks so geometry is derived from rendered characters rather than guessed x/y values.
10. **For learning/analysis scenes, do not rewrite source content just to explain it.** If a sentence, formula, paragraph or diagram already exists, keep it in place and attach `annotation` elements to the original target. Use `view` effects to temporarily fade unrelated content, walk through one logical layer at a time, then finish with a `restore` effect so the complete note is visible again. View effects are presentation transitions, not a second pen, and still occupy their own sequential timeline event.
11. **For short-video / vertical-video requests, optimize for phone readability instead of preserving a dense source composition.** Use `scene.pages` and `page` timeline events when one source image contains several independent modules. Prefer a 9:16-ish canvas such as 900×1600, one topic per page, large type, generous whitespace, a short completed-page hold, then a deterministic page turn. The first page may be a cover and the final page may be a recap. A completed gallery thumbnail shows the first page by default.
12. **Silent-video scenes must communicate without narration.** Every page needs a visible information hierarchy: fact/input area → visual explanation → concise takeaway. Do not leave a large dead lower half when a meaningful diagram, comparison, takeaway card or result can use that space. Keep the takeaway factual rather than meta commentary.
13. Within each video page, infer a real human drawing order from semantics rather than source z-order. Typical chart order is: write the explanation → draw chart frame/axes → draw ticks → write tick labels → draw/fill the data from its natural origin → write the final value or callout. Typical diagram order is: draw container/node → write its label → draw connector/arrow → move to the next node. Typical icon-caption order is: draw the icon first, then write its caption.
14. For colored bars or shaded regions, prefer one continuous dense serpentine/hatching stroke so the viewer sees the color being filled from left to right (or from the meaningful data origin) instead of a rectangle suddenly appearing. The completed state should read as a filled region, not a sparse comb. Keep these fills on the same single-pen timeline.
15. **Write for the viewer, not for the implementation.** Do not put meta copy such as “这一页只看…”, “先看参数…”, “一个页面记住…” or production instructions into the final handwritten canvas unless that sentence itself is valuable knowledge. Prefer concise facts, conclusions and labels. Use semantic `highlight` marks sparingly on the 1–3 most important numbers/phrases per page so the finished frame has a clear visual hierarchy.
16. For charts, never align multiple tick labels by inserting spaces into one text string. Each tick label must be its own positioned text element centered on the corresponding tick coordinate. Lock this relationship with a scene test when the chart is important.
17. Prefer normal line/box primitives and let the shared hand-drawn renderer add deterministic roughness. Use custom SVG paths for diagrams or irregular icons. Do not add scene-ID conditionals to `RecreationCanvas` or `RecreationStage`.
18. Register the scene once in `features/recreation/scenes/index.ts`. The history sidebar, gallery and `/scenes/<scene-id>` route should then appear automatically.
19. Add a scene structure test asserting the key content groups, diagrams, anchored annotations and intended choreography. For paged video scenes, assert page order, page-turn placement, and the semantic drawing order inside representative pages. Run scene validation and ensure no duplicate element IDs/orders, missing annotation/mark targets, invalid page references, invalid mark order or out-of-bounds boxes.
20. Compare the finished canvas against the reference at both full-page and detail level. Fix geometry/content errors in the new scene only. Do not change another scene to make the new image fit. If a missing capability is genuinely generic, extend the shared scene protocol/renderer with tests first, then use it from the new scene.
21. Paged scenes automatically generate a completed PNG for every page after the first full playback finishes and persist them under `artifacts/recreation/<scene-id>/final-pages/`. The save operation replaces the whole directory atomically, so stale images from a previous revision are removed. `manifest.json` records the current revision and page/file mapping.
22. Give actively iterated paged scenes a `snapshotRevision` string. **Increment it whenever scene content, layout, renderer behavior, or visual emphasis changes enough that the final frames should be reviewed again.** The revision is written to the snapshot manifest.
23. Treat generated final-page images as part of the QA loop. If `artifacts/recreation/<scene-id>/final-pages/` exists, inspect those PNGs before handoff. For silent-video scenes, check phone readability, dead space, overlap, visual hierarchy, highlighted facts, final takeaway, and whether each chart/diagram explains itself without audio. If a defect is found, revise the scene, increment `snapshotRevision`, rerun the first playback, and inspect the newly replaced PNG set.

## Recreation architecture invariants

- `RecreationCanvas` is rendering-only. It must not create a player, timer, `ResizeObserver`, toolbar or global state.
- `RecreationStage` owns the simulated conversation shell, playback, page transitions and responsive viewport scaling.
- The left history list comes from the registered scene list; handwritten scene data must not hard-code navigation UI.
- The user prompt is ordinary UI and is immediately visible. Only the handwritten assistant answer participates in the pen/presentation timeline.
- Static scene elements always render at progress `1`; replay/reset only clears dynamic progress.
- `annotation` elements anchor explanatory labels to an existing text range; they must not duplicate the source sentence as a second text block.
- `view` elements only control presentation opacity. Static paper structure stays visible, focus transitions must be deterministic, and completed thumbnails ignore temporary focus so they always show the full note.
- `page` elements are presentation transitions on the same sequential timeline. They do not draw ink; they switch from the current `pageId` to the target `pageId` only after earlier page content has completed.
- Final-page snapshots are presentation tooling, not scene content. They render each page with `completed=true`, must not mutate player progress, and must not block or stutter the first playback.
- The snapshot persistence API may write only under `artifacts/recreation/<safe-scene-id>/final-pages/`; page and scene IDs must be sanitized before filesystem use. Generated PNGs stay git-ignored.
- Scene routing is canonical and isolated by canonical scene ID. Old player callbacks must never update a newly mounted scene.
- `scene-registry.ts` is the authority for canonical IDs, aliases and validation.
- Unknown/unsafe scene IDs must resolve to 404. The legacy `photo-1-skill-agent-notes` alias permanently redirects to `skill-agent-notes`.
